# שלב 8: מוכנות תפעולית

> סטטוס: **הושלם** (2026-10-16). כל הסעיפים מומשו ואומתו.
>
> **אימות סעיפים 4–6:**
> - **החלפת מפתח:** Keyring (`SETTINGS_ENCRYPTION_KEY_PREVIOUS`) ו-CLI `rotate-key`. בדיקות: dry-run שאינו משנה דבר, הצפנה מחדש של 4 סוגי שדות, עצירה ללא שינוי כשהמפתח הישן חסר, הרצה חוזרת שאינה מזיקה, ו**בדיקת schema שנכשלת אם תתווסף עמודת `*_enc` בלי לעדכן את הכלי**. ב-Stack: התהליך המלא ללא השבתה. כניסת חירום וסודות הספקים עבדו לפני ההחלפה, במהלכה ואחריה, והמפתח הישן נדחה בסופה.
> - **install.sh:** קובץ במצב 600, בלי סודות בפלט. מסרב לדרוס קובץ קיים. דוחה קלט לא תקין בלי להשאיר קבצים חלקיים. ה-`.env` שנוצר עובר את ולידציית התצורה של השרת (production/oidc).
> - **מדריך:** `docs/10-user-guide.md`. כל שמות הכפתורים והמסכים אומתו מול הקוד.
>
> **ממצא בטיחותי שתוקן (החלטה פתוחה לאישור הלקוח):** אש שחזרה לשגרה ברכזת לפני שמישהו אישר אותה נעלמה מהמסך הפעיל, והצליל נפסק. **עכשיו אש וקדם-אזעקה שלא אושרו נשארים ברשימה** עם הסימון "חזר לשגרה ברכזת. ממתין לאישור", עד לאישור קבלה. אירוע חדש באותה נקודה מחליף את הקודם (`superseded`), כך שאין כפילויות. תקלות ואירועי תקשורת אינם ננעלים. מיגרציה 008.
>
> **אימות סעיף 3 (Break-glass):**
> - בדיקות שרת: 188/188, מהן 21 חדשות. כוללות את וקטורי RFC 6238 ו-RFC 4226, scrypt עם הגנה מפני פרמטרים מזויפים, תשובה זהה לכל סוג כישלון, דחיית קוד שכבר שימש, נעילה והתראה, rate limit, reset ו-disable שמנתקים sessions, תקרה של 3 חשבונות, וחשבון חירום שאינו מקבל התראות.
> - ב-Stack: מיגרציה 007 רצה כ-owner. ל-`fs_app` יש DML בלבד על הטבלה החדשה. ה-CLI רץ בקונטיינר.
> - E2E דרך Caddy: 16/16. הטופס מקופל כברירת מחדל ונפתח במקלדת, הודעת השגיאה כללית, שדות הסוד מתנקים, יש באנר קבוע, ה-session מוגבל לשעתיים, למשתמש אין קישורי ניהול, והתג מוצג אצל המנהל. axe נקי בכל המסכים.
> - הגבלת Caddy: 403 מחוץ לרשתות המותרות. ניסיונות עקיפה (query, XFF מזויף, `./`, אותיות גדולות, `%2D`) נחסמו כולם.
> - **ממצא UX שתוקן:** בשדה הקוד `maxLength` קטע את הקלט לפני שהרווח הוסר. הדבקה של "123 456" הפכה ל-5 ספרות.

## תוצאות אימות ה-Stack ב-Docker (סעיפים 1–2)

| בדיקה | תוצאה |
|---|---|
| בניית images (server, web, collector) | ✅ השרת רץ כ-`node`, read-only וללא dev deps; ה-collector רץ כמשתמש ייעודי |
| Least privilege | ✅ הטבלאות בבעלות `fs_owner`. ל-`fs_app` יש רק INSERT/SELECT על `audit_log`. ל-db ולשרת אין פורטים חשופים |
| Caddy + TLS | ✅ HTTP/2, אימות תעודה, כל כותרות האבטחה (CSP, HSTS, nosniff, Referrer, Permissions, COOP); ל-`sw.js` מוגדר `no-cache`. API ללא התחברות מחזיר 401 |
| ClamAV אמיתי | ✅ EICAR מזוהה (`Eicar-Test-Signature`). כשהסורק לא זמין מוחזרת שגיאה (fail-closed) |
| העלאה דרך ה-API | ✅ קובץ נקי: 201. קובץ שאינו תמונה: 415. **תמונה עם תוכן זדוני**: 422, נרשם Audit עם שם החתימה, התוכן נמחק (`content=NULL`) והתוכנית לא קושרה לקומה |
| Collector בקונטיינר מול הסימולטור | ✅ אש מגיעה לשרת. Ack וחזרה לשגרה עובדים. השרת הושבת: האירועים נשמרו ב-outbox (502 עם backoff) והגיעו לאחר החזרה. רכזת לא מגיבה וגם Collector שנעלם (watchdog) פותחים התרעת תקשורת שנסגרת אוטומטית |
| E2E בדפדפן דרך Caddy | ✅ 13/13 (פעמיים): secure context, עוגיית `__Host-` מסוג Secure/HttpOnly/Lax, RTL, axe, התרעה חיה ב-WebSocket תוך ~130ms, Ack, ביטול session ב-logout (עוגייה שנשמרה מחזירה 401), אין הפרות CSP |

**ממצאים שתוקנו:**
- **הפרת CSP (`script-src eval`) מ-Zod 4.** בזמן יצירת סכמות הספרייה בודקת אם `new Function` זמין. ה-CSP חסם את הבדיקה (תקין), אבל הדיווח על הפרה מסתיר הפרות אמיתיות. נוסף `apps/web/src/zod-csp.ts` עם `jitless`, והוא הייבוא הראשון בקליינט. בשרת אין CSP, ושם ה-JIT נשאר פעיל.
- **הערה על EICAR:** ב-ClamAV החתימה היא hash של הקובץ כולו (68 בתים), ולכן EICAR שמוטמע בתוך תמונה לא יזוהה. זו התנהגות תקינה של ClamAV ולא של המערכת. חתימות אמיתיות (ndb/ldb) מזוהות בכל מקום בקובץ. אימות המסלול המלא נעשה בחתימת בדיקה זמנית, שהוסרה בסיום.

## עיצוב: כניסת חירום (Break-glass), סעיף 3

**הבעיה:** כל הכניסות עוברות דרך Entra ID. אם Entra, האינטרנט של המוסד או ה-tenant אינם זמינים, מסך הניטור נשאר נעול, גם בזמן אירוע.

**העקרונות:** כבוי כברירת מחדל, יצירה רק ממסוף השרת, שני גורמי אימות, חשיפה מינימלית ותיעוד מלא.

| רכיב | החלטה |
|---|---|
| הפעלה | `BREAK_GLASS_ENABLED=false` כברירת מחדל. כשהוא כבוי ה-route לא נרשם (404) והקישור לא מוצג |
| יצירת חשבון | **CLI בלבד** (`docker compose exec server node apps/server/dist/cli/break-glass.js create ...`). הסיסמה (24 תווים אקראיים) וסוד ה-TOTP נוצרים בשרת ומוצגים **פעם אחת**. אין API ליצירה |
| סיסמה | scrypt (N=2^15, r=8, p=1) עם salt אקראי. ההשוואה ב-`timingSafeEqual` |
| MFA | TOTP חובה (RFC 6238: SHA-1, 30 שניות, 6 ספרות, חלון ±1). הסוד מוצפן ב-AES-256-GCM (המפתח `SETTINGS_ENCRYPTION_KEY`). **הגנה מפני שימוש חוזר:** קוד שכבר שימש נדחה (`last_totp_step`) |
| שגיאות | הודעה כללית אחת: "פרטי הכניסה שגויים". אין רמז אם השם, הסיסמה או הקוד שגויים. גם לשם משתמש שאינו קיים מריצים scrypt מול hash דמה, כדי שזמן התגובה יהיה זהה |
| Brute force | rate limit ל-route (5 לדקה לכתובת IP). **נעילה לחשבון**: אחרי 5 כישלונות ברצף, ל-15 דקות. Caddy מגביל את ה-route לרשתות פנימיות (`BREAK_GLASS_ALLOWED_CIDRS`) |
| Session | קצר: `BREAK_GLASS_SESSION_HOURS` (ברירת מחדל 2, מקסימום 4). מסומן `method='break_glass'`. **באנר אדום קבוע** בממשק: "מחובר בכניסת חירום" |
| הרשאות | Operator כברירת מחדל (צפייה ואישור קבלה). FireAdmin רק בדגל מפורש. ל-Operator מוקצים כל המבנים בזמן היצירה (פקודת `scope-all` מרעננת). חשבון חירום לא מקבל התראות |
| התראה ותיעוד | כל ניסיון (הצלחה, כישלון, נעילה) נרשם ב-Audit. **כל כניסה מוצלחת ונעילה שולחות התראה מיידית לכל ה-FireAdmins** בערוצים שלהם (דוא"ל, SMS, WhatsApp ו-Push אינם תלויים ב-Entra) |
| ניהול | CLI: `create`, `reset` (סיסמה ו-TOTP חדשים, ניתוק sessions), `disable`, `enable`, `list`, `scope-all`. בממשק המשתמשים מוצג תג "חירום" והחשבון ניתן להשבתה |

**נוהל מומלץ:** שני חשבונות לכל היותר. פרטי הכניסה מודפסים ונשמרים במעטפה חתומה בכספת של חדר הבקרה, ואפליקציית TOTP מוגדרת על מכשיר ייעודי. אחרי כל שימוש מבצעים `reset`. בדיקה רבעונית.
